## 1. H 与窗口重叠定义

### 代码位置

[src/models/windowing.py:19-32](../src/models/windowing.py#L19)

```python
def build_window(words: list[str], i: int, H: int) -> list[str]:
    if i < H:
        raise ValueError(...)
    window = words[i - H : i + 1]
    assert len(window) == H + 1
    assert window[-1] == words[i]
    return window
```

### 逐项核实

| 问题 | 结论 | 证据 |
|---|---|---|
| H 表示什么 | **preceding words 数量**,不含 target | 函数文档"返回 H 个历史词 + 当前目标词";`window[-1] == words[i]` 断言目标词是窗口最后一个元素,其余 H 个是历史 |
| target i 的实际输入 | `words[i-H : i+1]`(Python 左闭右开,等价于索引 i-H 到 i,共 H+1 个) | 直接读代码,非 `i-H+1:i+1` |
| 每个窗口实际长度 | **H+1**,不是 H | `assert len(window) == H + 1` 是运行时断言,非仅注释 |
| 每个目标是否恰好获得 exactly H 个 preceding words | 是,且强制:`i < H` 时直接 `raise ValueError`,**不做静默截断** | 同上;`first_eligible_index(H)` 返回 H,即故事内首个合格位置 |
| eligible_h128 是否排除故事开头 128 个 target | **是,精确排除 local_id 0~127 共 128 个** | [scripts/m0_build_frozen.py:109](../scripts/m0_build_frozen.py#L109):`"eligible_h128": local_id >= 128`;第 278-282 行有断言验证 local_id=128 合格、127 不合格 |
| 不同模型是否用了不同切片 | **否,四模型共享唯一实现** | [src/models/base.py:105](../src/models/base.py#L105) 是唯一调用 `build_window` 的地方;四个 adapter(pythia/mamba/rwkv/awd_lstm)均未各自实现 windowing,只提供 `tokenize_with_spans`/`forward_hidden` |

### 关于"相邻窗口重叠 H 还是 H−1"—— 需要澄清而非修复

这个问题**没有唯一答案**,取决于"重叠"具体指什么,代码里两种定义都存在且都自洽:

**定义 A:完整窗口(含 target)的位置重叠**
`build_window(i)` 覆盖位置 `{i-H,...,i}`,`build_window(i+1)` 覆盖 `{i-H+1,...,i+1}`。
交集 `{i-H+1,...,i}` 共 **H** 个位置——因为窗口 i 的 target(位置 i)在窗口 i+1 里变成了历史词。

**定义 B:纯历史槽位(不含 target)的原始位置重叠**
这是补充实验 C1 里实际断言并在真实数据上验证过的口径。
[实验补充/scripts/m4s_assert_impl.py:82-101](../实验补充/scripts/m4s_assert_impl.py#L82):

```python
# B: 相邻合法目标位置的 H-1 重叠(eligible 是连续整数区间,逐对检查)
origins_a = context_origins(perm, a, H)   # 历史槽位,不含target，H个元素
origins_b = context_origins(perm, b, H)
if not np.array_equal(origins_b[:-1], origins_a[1:]):
    b_failures.append(...)
```

`context_origins(i, H)` 只取 `{i-H,...,i-1}`(H 个元素,不含 target 本身)。
相邻两组的交集是 `{i-H+1,...,i-1}`,共 **H−1** 个。这条断言在 84 个真实故事、
443,286 对相邻窗口上跑过,**0 处失败**(见 [实验补充/结果总记录.md](../实验补充/结果总记录.md))。

**结论**:代码没有错,是两种合法但不同的计数口径。**需要做的是去检查论文/摘要
实际写的是哪一种表述**,若写的是"H−1 overlap"且指的是定义 A(含 target 的窗口),
则应改成 H;若指的是定义 B(纯历史槽位),则 H−1 本身没错,但建议在方法部分显式
说明"不含 target 词本身"以避免歧义。**本文档无法直接读取当前论文文本**
(只能读到仓库内 `manuscript/methods.md`/`results.md`,均未检索到相关表述,
正式稿在 `.docx` 中未能提取比对),这一步需要你对照论文原文核实。

### 代码位置

```python
def shift_story_no_wrap(X, seconds=40.0, tr=2.0):
    d = int(round(seconds / tr))
    out = np.zeros_like(X)
    valid = np.zeros(nt, dtype=bool)
    if d > 0:
        out[d:, :] = X[:-d, :]
        valid[d:] = True
    ...
    return out, valid
```

### 逐项核实

| 问题 | 结论 | 证据 |
|---|---|---|
| shift 方向 | **延迟(delay)**:`X_shifted(t) = X(t-40s)`,即用**更早**的特征去预测当前响应 | 函数 docstring 明确写出该公式;正 `seconds` 值 → 特征相对响应"延后" |
| 20 TR 具体如何移动 | `d = round(40/2) = 20`;`out[20:] = X[:-20]`,即输出数组第 t 位放原数组第 t-20 位的值 | 直接读代码 |
| 是否用 `np.roll` 产生 wrap-around | **否**。显式 `np.zeros_like` 置零 + 布尔 `valid` 数组,**未使用** `np.roll` 或任何循环位移 | 全函数搜索确认无 `roll` 调用 |
| 移出范围的 TR 如何标记 | 越界的前 20 个 TR 保持 `out=0`(零填充)且 `valid=False`,显式标记,供下游掩码使用 | 同上;`valid` 数组初始化为全 False,只对有效区间置 True |
| normal 与 shift 是否真的使用相同 mask | **是,且有运行时强断言,不一致直接 raise** | 见下方专项说明 |
| common mask 是否排除 shift 后无特征的 TR | 是,通过 `shift_valid_by_story` 参数传入 `run_fold`,与 FIR-valid、>100s 掩码取交集 | [src/ridge/pipeline.py](../src/ridge/pipeline.py) 的 `run_fold` 签名与内部逻辑 |
| FIR 在 shift 之前还是之后 | **shift 在前,FIR 在后**:shift 作用于降采样后、PCA/FIR 前的原始特征(`StoryData.X`),`run_fold` 内部才做 PCA→FIR | [src/ridge/m4_driver.py:56-58](../src/ridge/m4_driver.py#L56) 的 `make_shifted_story_data` 直接对 `sd.X` 做位移;`_transform_and_fir` 在 `run_fold` 内部才调用。**副作用**:shift 条件下 4 档 FIR 延迟(2/4/6/8s)实际探测的是相对真实响应 42/44/46/48s 的延迟,这是负控制设计的自然结果,不是 bug |
| PCA 和 ridge 是否在 shift 条件下重新拟合 | **是,完全独立重新拟合** | 见下方专项说明 |

### normal/shift 掩码一致性 —— 运行时强断言,非事后核查

[src/ridge/m4_driver.py:146-181](../src/ridge/m4_driver.py#L146):

```python
fr_normal = run_fold(story_data, train_s, test_s, ..., shift_valid_by_story=shift_valid)
...
fr_shift  = run_fold(shifted_data, train_s, test_s, ..., shift_valid_by_story=shift_valid)

for a, b in zip(fr_normal.story_scores, fr_shift.story_scores):
    if not np.array_equal(a.scoring_mask, b.scoring_mask):
        raise ValueError(f"...normal 与 shift 评分 mask 逐元素不相同 → 非共同 mask,配对不成立")
```

`train_s`/`test_s`(同一折)对两次调用完全相同;`shift_valid` 同一份传入两次。
比对不是"n_eff 相等"这种弱检查,而是**逐元素 `np.array_equal`**,不一致直接抛异常
终止运行——这意味着**如果这个问题真实存在,当前已跑出的正式结果就不可能是错的**
(错的话程序会在生成结果前就崩溃),这是比"我读代码觉得应该没问题"更强的保证。

### PCA/ridge 重新拟合

`fr_shift = run_fold(shifted_data, ...)` 是对 `run_fold` 的**完全独立第二次调用**,
而 `run_fold` 内部逻辑(已在模块 5 详细核实)是"scaler/PCA/λ 只在当前调用的训练折
数据上 fit"。由于两次调用传入的 `story_data` 不同(一份是原始,一份是位移后),
scaler/PCA/ridge **各自独立拟合**,不存在复用同一套参数的情况。

### "保持 target 不变"与"story-level permutation"能否同时成立

**能,且这不是需要担心的张力,是构造上的必然**。原因:置换 `perm` 只作用于
**历史槽位的取值来源**(`context_origins` 返回的是"要从原故事的哪个位置取词"),
从未作用于 target 本身——target 在 `build_perturbed_window` 里是硬编码
`words[i]`,完全绕开了 `perm` 数组。即使 `perm` 把位置 `i` 映射到了别处
(即真实词 `words[i]` 的内容被用作了**别的**目标的乱序历史),这也不影响
"target i 自己的取值"这件事,因为 target 的读取路径根本不经过 `perm`。

### normal/C1 掩码一致性验证

[实验补充/scripts/m4s_ridge_perturbed.py:98-158](../实验补充/scripts/m4s_ridge_perturbed.py#L98):
`reference_scoring_masks` 从 `respdict` 直接算出 normal 条件的掩码(不加载任何特征/BOLD,
纯元数据推导),与 C1 的 `run_fold` 产出的 `scoring_mask` 逐元素比对,记录
`n_mask_difference`(设计上应恒为 0)。这与模块 2 的 normal/shift 验证是同一种
"运行时断言而非事后目测"的模式。

## 4. Bootstrap、p 值与置信区间 —— **发现一处需要澄清措辞的真实问题**

### 代码位置

[src/stats/bootstrap.py:120-133](../src/stats/bootstrap.py#L120)

```python
def bootstrap_two_sided_p(values: np.ndarray) -> float:
    v = values[np.isfinite(values)]
    p_le = float((v <= 0).mean())
    p_ge = float((v >= 0).mean())
    return min(1.0, 2.0 * min(p_le, p_ge))
```

### 逐项核实

| 问题 | 结论 | 证据 |
|---|---|---|
| bootstrap 次数是否确实 1000 | **是** | [config/config.yaml:95](../config/config.yaml#L95):`bootstrap_iterations: 1000`;[scripts/m5_analysis.py:151](../scripts/m5_analysis.py#L151) 读取该值作为默认 `n_boot` |
| CI 方法 | **纯 percentile 法**,不是 BCa 也不是 basic/pivot | [src/stats/bootstrap.py](../src/stats/bootstrap.py) 的 `percentile_ci` 只调用 `np.percentile`,无偏差校正、无加速度校正 |
| 双侧 p 值公式 | `p = 2·min(P(θ*≤0), P(θ*≥0))`,截断到 [0,1] | 同上,与你贴的可疑写法**形式一致** |
| 是否用 plus-one correction | **否** | 公式里就是 `(v<=0).mean()`,分母是 `v.size`(即 n_boot),分子没有 +1;详见下方 |
| 无 draw 越过零时是否直接返回 0 | **是,会直接返回 0.0** | 若 1000 次抽样全部同号,`p_le` 或 `p_ge` 中有一个精确等于 `0.0`,`2*0.0=0.0` 原样返回,无下限保护 |
| Holm 校正是否每被试分别对两个对比实施 | **是** | `scripts/m5_analysis.py` 按 `--subject` 逐被试独立运行一次;[src/stats/estimands.py:23-26](../src/stats/estimands.py#L23) 的 `CONFIRMATORY` 列表固定 2 项;[scripts/m5_analysis.py:178-179](../scripts/m5_analysis.py#L178) 每次运行只对这 2 项做 Holm(`m=2`) |
| Table 4 的 `p<0.001` 如何生成 | 由展示层 `fmt_p` 把原始 p 格式化,`p<0.001` 时显示为该字符串 | [src/viz/m6_style_v2.py:108-123](../src/viz/m6_style_v2.py#L108):`if p < 0.001: return "p<0.001"` |
| CI 是否做 multiplicity adjustment | **否**,只有确认性家族的**显著性判定(星号)**经 Holm 校正,展示的 **CI 本身是未校正的原始 95% 区间** | `fmt_p` 函数文档明确写"刻意不加 Holm-adjusted 前缀""图上如实标原始 p" |

### 关键发现:真实数据确实产出过 p=0.000

你贴的可疑写法与仓库实际代码**逐字符一致**(除变量名)。这不是一个假设性风险——
在本会话早前对论文数据的核对中(见 `milestone/` 下的论文核查记录),已确认
**Table 4 中至少一个确认性对比的原始 bootstrap p 值就是精确的 0.0000**,
经 `fmt_p` 显示为 `p<0.001`。

**这是否构成需要重跑的错误?——不是,但展示口径需要调整**:

1. `p<0.001` 这个**展示字符串本身没有撒谎**:0.0000 确实小于 0.001。
2. 但**如实报告应该更进一步**:1000 次 bootstrap 的统计分辨率下限是
   `1/1000 = 0.001`;若用你建议的 plus-one 校正(`p=(count+1)/(n_boot+1)`),
   理论最小值是 `2×1/1001 ≈ 0.002`,**永远不会精确等于 0**。当前代码给出的
   精确 0.0000,反映的是"1000 次里没有一次跨越 0"这个**离散计数事实**,
   而不是"真实 p 值被测量为 0"——这是有限 Monte Carlo 抽样的分辨率下限,
   不是真实显著性水平的估计值。
3. **建议**(不需要重跑,是统计报告层面的修正):
   - 论文中明确写出这是"未校正的原始百分位法双尾 p 值,分辨率受 n_boot=1000
     限制,最小可测非零精度为 1/1000",而不是暗示 p 值被精确估计到了 0.000;
   - 或者按你的建议改用 plus-one 校正公式重新计算(这只是对 `draws` 数组重新
     算一遍 p,**不需要重新做 bootstrap 抽样本身**,`draws` 已经落盘,是纯 CPU
     的二次计算,几分钟内可以跑完并生成新的 p 值表);
   - 两种做法都不影响任何点估计、CI 或 Holm 拒绝的结论方向,只影响 p 值的
     文字精度声明。

| test stories 是否完全没有进入 Scaler/PCA | **是,完全没有** | `run_fold` 第 1 步:`Xtr_raw = np.vstack([story_data[s].X for s in train_stories])`;`scaler.fit`/`pca.fit` 只作用于这个 `Xtr_raw`。测试折在第 3 步才出现,且只调用 `scaler.transform`/`pca.transform`,从未调用 `.fit` |
| inner-validation stories 是否参与了 PCA 拟合 | **有,这是需要在方法里说明的常规做法,但不构成 outer-test 泄漏** | 见下方专项说明 |
| λ 选择是否只使用 outer-training stories | **是** | inner CV(`KFold(n_splits=inner_folds)`)作用于 `Xtr_f`,而 `Xtr_f` 来自 `_transform_and_fir(story_data, train_stories, ...)`——只包含 outer-training 故事的行 |
| final ridge 是否在选择 λ 后用全部 outer-training stories 重拟合 | **是,两个 solver 都明确重拟合** | numpy 版:代码注释"用全训练集按所选 λ 拟合并预测测试集",`XtX = Xtr.T @ Xtr` 用的是完整 `Xtr`;himalaya 版:`solver_params` 里有 `n_targets_batch_refit=2000` 参数,注释"全训练集 refit 阶段同样分块"——参数名本身就叫 refit |

### 关于 inner-validation 与 PCA 的关系

`run_fold` 的执行顺序是:**先在全部 outer-training 数据上 fit 一次 scaler/PCA**,
然后 λ 选择的 inner K-fold 才在**已经过 PCA 变换后的** `Xtr_f` 上操作
(himalaya 的 `KFold` 直接切分 `Xtr`/`Ytr`,即 PCA 之后的特征)。

这意味着:inner-validation 那部分故事的原始特征,**确实参与了 PCA 基向量的拟合**
(因为 PCA 是在切 inner fold 之前、对全部 outer-training 数据一次性 fit 的)。
这**不是**"outer test 泄漏"(outer test 从头到尾没有被 PCA/scaler 看到过),
而是"PCA 相对 inner-validation 的常规温和泄漏"——在深度学习/传统 ML 里,
"先对整个训练池做无监督预处理,再对同一训练池做超参数交叉验证"是普遍做法,
通常不视为需要修复的数据泄漏,但**严格来说会让 λ 的 inner-validation 分数
略微乐观**(因为 inner-val 的信息以一种间接方式影响了它自己被投影到的坐标系)。

**建议**:这一点如果论文的 Methods 部分描述为"PCA 与 inner-validation 完全独立",
则表述不够精确,应改为"PCA 在 outer-training 全体上一次拟合,λ 的 inner
cross-validation 在 PCA 变换后的特征上进行"——这是如实描述当前代码行为,
**不需要改代码或重跑**,除非你们认为这种温和泄漏不可接受(那样才需要改成
"每个 inner fold 各自重新 fit PCA"这种更严格但计算量更大的方案)。

### hidden_states 层号约定 —— 有运行时断言,但未核实 pre/post final norm

三个 transformer/SSM 模型(Pythia/Mamba/RWKV)都遵循相同约定:
`output_hidden_states=True` 返回长度 `n_layers+1` 的 tuple,`hidden_states[b+1]`
= 第 b 个(0-based)block 的输出。**每个 adapter 的 `load()` 里都有
`_assert_layer_convention()`**,在真实加载的模型上跑一次前向、断言
`len(hidden_states) == n_layers + 1`,不是只在注释里声明。

**未覆盖的一点**:HuggingFace 的因果语言模型实现里,`hidden_states` 元组的
**最后一个元素**(对应最终层)通常是**最终 LayerNorm 之前**的 block 输出
(最终 LN 只在计算 `lm_head` 的 logits 前才应用)——这是 GPT-2/GPTNeoX 系列
的常见实现方式,但代码里**没有显式断言或注释确认这一点对 Pythia/Mamba/RWKV
三者是否都成立、是否一致**。三个模型的 HF 实现可能在这一点上有细微差异
(尤其 Mamba 和 RWKV 的 HF 移植版本相对较新,不能完全假设与 GPT-2 系一致)。

**建议**:补一次简单核实——在服务器上分别对三个模型跑一次前向,比较
`hidden_states[-1]` 与"手动应用最终 LN 后的结果"是否相同,确认三模型口径一致。
这是纯诊断性质的检查,**不需要重跑任何已有结果**,除非发现不一致才需要决定
是否调整"final layer"的取值点。

### state reset —— 四模型机制不同,风险集中在 AWD-LSTM

| 模型 | `reset_state()` 实际做什么 | 为什么 |
|---|---|---|
| Pythia | no-op(空函数体) | Transformer 每次 forward 天然无跨调用状态(`use_cache=False`) |
| Mamba | no-op | HF 实现里 SSM latent 默认从零状态开始,不传 `cache_params` 即天然冷启动 |
| RWKV | no-op | 同理,不传上一窗 state 即天然冷启动 |
| **AWD-LSTM** | **调用 `self.encoder.reset()`,真实清空 hidden/cell state** | fastai 的 AWD_LSTM 实现**确实会跨调用缓存 hidden state**,是四个模型里唯一需要主动清空的 |

前三个模型的"reset"是 no-op 不代表没有检验——`test_state_reset_positive_and_negative`
([tests/test_m1_windowing.py:182](../tests/test_m1_windowing.py#L182))用一个能模拟状态继承的
`FakeAdapter` 做了双向测试:**两次冷启动结果必须相同**(正向)、
**故意不重置结果必须不同**(反向)。这条测试证明了"重置机制在被正确调用时确实生效",
不是没测过。

**AWD-LSTM 有一处代码作者自己标记的未验证风险**
([src/models/awd_lstm_adapter.py:117-123](../src/models/awd_lstm_adapter.py#L117)):

```python
def forward_hidden_batch(self, token_id_lists, layers: LayerSpec):
    """...
    ⚠️ AutoDL 上需核验：fastai AWD_LSTM 跨调用缓存 hidden，要求 reset() 后
    按当前 batch 大小重新初始化；末批 batch 较小时务必确认 reset 生效。
    """
```

这段注释直接承认:fastai 的 AWD_LSTM 内部缓存的 hidden state 张量形状与**上一次
forward 的 batch 大小绑定**。若 `reset()` 没有正确按**当前**批大小重新初始化
(而不是复用上一批的形状),在批大小变化的边界——**最典型的就是每个故事最后一个
不足 32 的尾批**——可能出现状态复用错误。

### 这个风险是否已被现有测试覆盖?—— 部分覆盖,尾批场景未覆盖

真实模型上的批量正确性闸门是 `verify_batch_matches_single`
([scripts/m1_extract_features.py:50-69](../scripts/m1_extract_features.py#L50)):
在**真实加载的模型**(非测试用假模型)上,取前 `n`(默认 4)个目标,分别用单条
`extract()` 和整批 `extract_batch(batch_size=len(sample))` 提取,逐元素比较,
容差外直接 `assert` 失败。注释明确写"这是批量路径的正确性闸门:right-padding/mask
的 bug 会让目标 hidden 大幅偏离,而非 ~1e-4"。

但这个默认检查**只构造了一个大小为 4 的单一批次**,不包含"batch_size=32 的常规批
后紧跟一个更小尾批"这种转换场景——**恰好是 AWD-LSTM 那条警告注释点名的场景**。
本地的 `test_extract_batch_matches_single`(用 `FakeAdapter`)同样不能补上这个缺口,
因为 `FakeAdapter.forward_hidden` 的输出只依赖位置索引和固定的 `self._carry`
标量,**不依赖真实的批内其他样本内容**,无法揭示"batch 形状变化导致状态复用错误"
这类问题(这类假模型本来也测不了真实的 fastai 内部缓存行为)。

**建议**(优先级最高的一条,建议在提交前确认):
在服务器上针对 AWD-LSTM,构造一个"先跑一个 32 的批,再跑一个更小的尾批(如 5)"
的场景,用 `verify_batch_matches_single` 同样的单条 vs 批量比对逻辑,专门检查
尾批那几个目标的 hidden 是否与单条提取一致。这是一次性的诊断脚本,**读已有缓存
特征或临时跑几十个词级前向即可**,不需要重跑整个提取流程,预计几分钟内出结果。
若比对通过,这条风险可以正式排除;若不通过,需要定位是 `reset()` 时机问题还是
fastai 内部 batch 维度处理问题,再决定是否需要重跑 AWD-LSTM 的特征提取
(注意:AWD-LSTM 是"历史参照模型",不参与核心三模型架构排名的确认性结论,
即使需要重跑,也不影响 Mamba/Pythia/RWKV 的比较结果)。
